## Minimal implementation direction

A per-`NetState` deferred **world-item producer** is a reasonable narrow design. It should hold bounded entity references, then invoke the original complete `SendInfoTo(state, sendOplPacket)` on the main game thread after revalidation. It should not become a second unbounded packet/byte queue. Keep the hard 96 KiB queue guard, original serialization, skill progression and house storage rules unchanged.

Required properties of that design:

1. Share one producer between full-view, walking-entry and core world-item broadcast paths. Maintain a small immediate-work budget across calls/time slices, not a fresh allowance per item. When the socket drains rapidly, a per-call allowance would still let one full enumeration do all packet-building synchronously. Bound deferred work and scans per callback and keep at most one outstanding drain timer per connection.
2. Use pending-byte backpressure under the existing send-queue synchronization. A read-only conservative pending-byte estimate is sufficient; no accounting rewrite is needed. Leave room for login, movement, speech and other control packets. An item-count limit alone does not bound bytes.
3. Store one pending entry per item and merge repeated requests. Promote the optional-OPL flag from false to true when any coalesced request needs it. Before delivery recheck the original connection/mobile identity, socket/disposal/blocking state, item deletion, `Parent == null`, non-Internal matching map, current range and `CanSee`. Build packets at delivery so changes are current.
4. Stop and clear pending work on connection disposal or mobile reassignment. Define view/map-generation cancellation explicitly. A queued item that moves into a container, becomes hidden, is deleted or leaves range must not reappear after a remove packet. A map switch and return to the same map must not revive an obsolete callback. Do not merely capture a map pointer and assume it distinguishes generations.
5. `Dispose` can originate from network callbacks; avoid racing timer queue access with disposal cleanup. Do not hold the pending-work lock while calling virtual item methods or while acquiring unrelated send/disposal locks. Test reentrant enqueue and stale callbacks; no orphaned timer/reference retention should survive disconnect.
6. The soft budget must reserve space for a **whole virtual item packet group**. The ordinary HouseFoundation group is small, but source provides no general hard bound for `Corpse.EquipItems`. A fixed reserve is not proof that arbitrary malformed/huge groups fit. Measure valid groups and retain an explicit diagnostic/fail path for a single oversized group rather than silently dropping its tail or increasing the hard cap. Record this limit honestly if it remains outside the normal supported envelope.
7. Choose and measure a finite per-connection deferred-entry ceiling. A 32,768/65,536-entry queue is bounded but materially costs memory across many clients. At exhaustion, report the count and location and fail explicitly; do not silently leave a permanent partial view. Avoid retaining a pooled world enumerator across timer ticks; free all pooled enumerables in `finally`.
8. Preserve existing immediate interaction responses unless separately required/tested: failed lift recovery (`Mobile.cs:4919-4935`) and the explicit customization handshake (`HouseFoundation.cs:828-835`) are not bulk nearby producers. Broadly intercepting every `Item.SendInfoTo` call can delay protocol prerequisites. If they are routed, add corresponding packet-order and interaction tests.
9. Keep per-item world/OPL/Corpse/HouseFoundation group order and the login/self/map/control prerequisites. An initial item-only design would move deferred world groups after `LoginComplete`; this was flagged as an ordering change and is superseded by the FIFO proposal below. The refined design retains packet order but lengthens login delivery, which still needs actual-client timeout and old/SA/HS packet characterization.
10. Resolve clear-screen behavior before claiming general travel recovery. Old removals must not run after new-view arrivals and erase the new view. The refined proposal below introduces ordered compact removals and view generation cancellation. Test it explicitly; merely suppressing all removals is unsafe, especially because distinct shard maps can share a client facet.
11. Rate-limit observability without enumerating the whole world again in an overflow handler. Useful fields are character serial, map/location, reason, admitted/deferred/coalesced/skipped count, byte estimate and queue high-water mark. Exclude credentials/account identifiers. Diagnostic exceptions or stalled output must not block delivery/escape; `Core.WriteDiagnostic` catches exceptions but still calls synchronous `Console.WriteLine` (`Main.cs:85-91`), so catch-only logging is not proof of nonblocking behavior.

These are technical containment choices, not new balance or eligibility policy. No policy decision is needed to retain the current rejection-output behavior, keep existing stored items, and provide recoverable bounded transmission. Any proposal to delete old piles, alter house decay, cap home storage, or silently omit items is a different gameplay/storage decision.

### Refined FIFO proposal received during review

The parent refined the design to one bounded work queue per connection: at most 65,536 logical entries containing item references, compact removal serials, or copied generic packet buffers whose combined backlog is capped at 96 KiB. `ClearScreen` advances the view generation and queues removals before map/control packets. Once deferred work exists, ordinary sends also join the FIFO. A 25 ms game-thread drain sends at most 64 world entries and examines at most 512 entries, using a 16 KiB pending-byte threshold. Each complete virtual item group is captured in at most 64 KiB of raw packet bytes, encoded only when dispatched, and enqueued atomically. Capacity/group limits cause an explicit diagnostic and the existing connection failure outcome, not silent item loss. Worker-thread `Dispose` only signals; collection cleanup runs in the game-thread disposal queue/mobile setter.

This is a proposed implementation, not reviewed code. It addresses the identified login/clear-screen ordering problem without changing the hard send queue cap. It is broader than the original item-only idea, so the following additional acceptance constraints apply:

- A 64 KiB **raw** group bound is not a bound on encoded bytes. An encoder may expand output and may hold stream state. Encode each packet exactly once in FIFO order, copy its encoded result before the next call can reuse a buffer, bound the aggregate encoded group and enqueue it under one send-queue lock. If encoding/group dispatch fails after the encoder advances, terminate that connection; never silently discard bytes and reuse the advanced encoder state.
- Preserve packet lifetime: copy the valid compiled segment before exactly-once `Packet.OnSend`/release. Static/acquired/pooled packet variants and shared buffers need targeted tests. The queued copy must not reference later-reused packet storage.
- Count generic and removal entries toward the callback examination ceiling. Enforce the generic-byte backlog limit on every admission, release the charge on dequeue/cancellation, and include in-flight capture/encoded buffers when describing bounded memory.
- Invalidated item entries can still occupy the logical ceiling until examined. Repeated map changes/redraws must not grow retained stale generations unchecked; safely compact/coalesce or demonstrate explicit bounded exhaustion and recovery. Do not reorder generic packets across removals while compacting.
- `LoginComplete` now waits behind the paced view as it did behind the original synchronous view. Test time-to-login at the supported density, slow consumers and continued control handling. Server-side `EventSink.Login` has historically run after enqueueing, not after wire delivery; do not mistake that callback for client login completion.
- Direct lift/customization packets remain ordinary sends, but FIFO can defer them behind a backlog. Test their prerequisite/result ordering under pressure even though their call sites are not changed.

The earlier item-only concerns remain in this report as design history where explicitly identified; they are not presented as the final implementation.

### F05-R1 — coalescing across a removal can erase a reappearing item (P1)

**Found in the first draft; source correction present, behavioral regression pending.** `SendWorldItem` initially merged any pending entry for the same item/view generation. `CaptureOrQueueWorldPacket` could subsequently append an ordinary `RemovePacket`, but did not make that earlier incoming entry ineligible for merging. Core ordinary item moves (`Item.cs:1734-1757,5606-5627`) provide the real producer sequence; this is not limited to a custom override.

Reproduction sequence: queue item A behind pressure; move A out of range so its normal remove packet joins the FIFO; return A before draining. The second incoming merges into the original entry. Drain builds A's latest visible state, then sends the intervening removal, leaving no later incoming. The client loses A until another refresh despite A being visible on the server.

The parent added `m_WorldSendCoalesceEpoch`, stored it on incoming entries, and requires matching view generation **and** epoch to merge. Generic packet and compact removal admission advance the epoch. Inspection of the updated draft (`NetState.cs:820-833,849,1046-1049`) confirms the proposed barrier is present. Required fixture cases: normal move-out/return, hidden/visible with remove, explicit removal, and duplicate same-barrier OPL promotion. Do not mark behavioral verification passed from this source inspection alone.

### F05-R2 — existing worker-thread sends race the new global queue (P1)

**Open at the first implementation inspection.** The draft assumes world work is game-thread-owned, but it also changes every `NetState.Send` through unsynchronized `CaptureOrQueueWorldPacket`, which reads/writes a `Queue<>`, dictionary-related state, byte accounting and capture list. Existing source sends from worker threads:

- `Data/Scripts/System/Misc/Console.cs:38,80-85,156-168,146-152`: `ThreadPool` console input calls `Next`, which broadcasts with `Mobile.SendMessage`. The page response worker also calls `SendGump` (`:110,130`). This facility is configurable; its setting does not establish safety for a newly unsupported call pattern.
- `Data/Scripts/System/Chat/General/IrcConnection.cs:164,293-306,319-326,286-290`: the IRC reader thread directly calls `BroadcastRaw`, which sends mobile messages; ordinary channel broadcasts also originate from `HandleInput` (`:401`).

If a worker sends while a world item is being captured, its unrelated packet can enter that item's `m_WorldSendCapture` and be discarded when the item's generation/visibility becomes stale. If it sends during draining outside capture, `m_DrainingWorldSend` makes it bypass the pending FIFO and race stateful encoding. Other timings can race queue enqueue/dequeue/clear or lose byte accounting. Synchronizing only socket `Dispose` cleanup does not fix these paths.

Required correction: define one serialized admission/encoding boundary for all send callers, with a bounded synchronized handoff for off-thread packets or equivalent locking/explicit capture ownership. Do not add an unbounded per-packet timer queue or allow worker packets into a game-thread item's capture. Preserve FIFO and encoder state and avoid deadlocks with the existing send-queue and timer locks. Required tests include background sends during a blocked/stalled item capture, while draining, and during disposal/reassignment; verify exact packet identity/order, bounded accounting and no capture contamination. The custom-house compression worker was separately checked: it marshals its final send through `Timer.DelayCall` (`HouseFoundation.cs:2888-2892,2916-2922`) and is not itself evidence of an unsafe direct worker send.

### Inspected non-issues and outstanding acceptance limits

- Captured packet segments are copied before `Packet.OnSend`; `Packet.OnSend` can return pooled buffers (`Network/Packets.cs:4614-4630`), so that copy is necessary. Group dispatch writes each encoded packet to its `MemoryStream` before encoding the next packet, then bounds encoded aggregate size. This addresses scratch-buffer reuse for the game-thread group path; it does not resolve R2's concurrent encoder access.
- The pending-byte property preserves the previous conservative queue calculation and the 96 KiB hard limit. The group path starts below the 16 KiB threshold and caps encoded group bytes at 64 KiB. Generic packets still need large/expanding-encoder acceptance: a 96 KiB generic backlog cap alone is not a proof that any one generic packet fits beside pending bytes.
- View invalidation retains ordered removes/control packets, while queued incoming entries are checked against the current generation and current visibility/map/parent. A stopped timer can still have an already queued `OnTick` because `Timer.Slice` calls it without checking `Running` (`Timer.cs:398-409`); the callback must remain harmless against current state after cleanup. Exact stale-callback and reconnect tests are still required.
- Compact removal entries currently retain `Item` references rather than only serial integers. They remain entry-bounded, but the final documentation should describe the actual storage and tested memory bound accurately.
- Item packet overrides can reenter state/session operations. Reassignment or a view change during capture must discard only stale world output and must not accidentally discard the new session's control traffic. Test this along with throwing overrides; existing normal Corpse/HouseFoundation paths do not themselves reassign the session.
