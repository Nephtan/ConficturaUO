## Review finding and resolution

### RV-01: synchronous diagnostic output can stall region entry

Priority: P1 for the stated requirement that reporting cannot block gameplay. Initial draft location: `Data/Scripts/Mobiles/Base/PlayerMobile.cs:1840-1855`, specifically `Console.WriteLine` at 1851. `BaseRegion.OnEnter` invokes this path directly at `Data/Scripts/System/Regions/BaseRegion.cs:255`.

The draft contains output exceptions and sets its five-minute per-character throttle before writing, which correctly prevents an exception/retry loop. However, output still runs synchronously on the entry callback. The production `FileLogger.WriteLine` opens, appends and closes a file synchronously (`Data/System/Source/Main.cs:908-920`), and `MultiTextWriter.WriteLine` invokes each sink directly (`Main.cs:957-965`). A stalled writer or filesystem can therefore hold the callback before any exception occurs. Per-character throttling also does not bound queued work across different characters.

Recommendation: make delivery bounded and nonblocking for the caller, passing only an immutable diagnostic snapshot to background work; bound outstanding work and contain delivery failure. Add a controlled blocked-writer test that proves entry returns while delivery is stalled, then release the test writer and clean up. Do not introduce gameplay mutations as a fallback.

Source resolution reviewed: the revised `PlayerMobile.cs:1842-1896` uses a single global `Interlocked` work slot, an immutable string snapshot and `ThreadPool.QueueUserWorkItem`. The worker writes a dedicated `Logs/SkillVerification.log` file, so it does not acquire the shared console writer. Queue rejection/exception releases the slot; worker output exceptions are contained and release it; a stalled writer occupies at most the single slot and does not access a Mobile. The updated fixture includes controlled blocking, throwing output, 100 distinct characters while the slot is busy, actual file output, an exclusive file lock and subsequent recovery. **Resolved: final regression log reports all 817 protection assertions passing, including these assertions.** Queue rejection is source-reviewed; a rejected ThreadPool enqueue was not forcibly injected.

Accepted observability limit: diagnostics are best effort. A busy slot drops new reports and their already-set per-character throttle prevents another attempt for five minutes; shutdown can lose a pending report. A permanently stalled sink occupies one background worker until process exit. Preservation and gameplay do not depend on report delivery. This bounded loss must be stated in the operational report; the log is not a complete audit trail.

## Confirmed source facts and intended behavior changes

- Baseline `SkillVerification` rejects cap 12000 even if both cached and independently summed bases are 5000. Its failure branch calls `SkillBegin`, clears profession and every base, and can reset stat cap and all raw stats (baseline `PlayerMobile.cs:1774-1901`). This is sufficient to explain the original 500.0/1200.0 wipe without claiming excess or cheating.
- The inspected draft removes all progression setters from this path, independently sums `BaseFixedPoint` in a `long`, and distinguishes real excess, cache mismatch, unrecognized legacy cap, profession/virtue mismatch, component mismatch and false Player flag. It does not turn the numeric whitelist into a new eligibility policy.
- `GetKeys` calls `SetKeys` before reading (`PlayerSettings.cs:1192-1200`); `SetKeys` rewrites `CharacterKeys` (`1269-1408`). The draft instead reads the tenth Virtue slot and preserves null, malformed and uninitialized records. For the relevant exact `"1"` slot, the diagnostic interpretation agrees with the old getter without its normalization side effect.
- Removing accepted-branch correction also preserves `Profession == 1` on non-fugitive numeric tiers. Previously the 10000/15000, 11000/16000 and 40000/45000 branches cleared it. Existing profession-based behavior will consequently continue instead of being silently cleared; for example `BaseRegion.OnEnter:247-253` still ensures at least one kill before validation. This is intentional preservation, not a claim that all surrounding gameplay is unchanged. Do not weaken profession eligibility elsewhere to accommodate it.
- Component disagreements remain unchanged during travel. Existing `PlayerMobile.Deserialize` still migrates/recalculates `Skills.Cap` from origin/boost/Ether (`PlayerMobile.cs:4572-4654` in the final source). A later load can therefore expose or change a cap independently of this repair. FIX-03 owns that policy; the repair must not claim arbitrary inconsistent caps are preserved through load.
- `SkillCheck.Gain:645-735` is untouched. With truthful Player/cache state its final aggregate guard remains, including normal at-cap rejection. Known false-cache/Player bypasses, direct grant paths, acceleration loss and individual-cap overshoot remain follow-ups. A preserved invalid character is not automatically repaired or sanctioned by FIX-01.
- `Skills` index access may lazily materialize a zero-valued default Skill (`Data/System/Source/Skills.cs:1474-1492`); the real-sum scan does not set skill bases/caps/locks or cached totals. The new per-player diagnostic timestamp is not serialized. No serialized read/write order is changed in the inspected diff.
