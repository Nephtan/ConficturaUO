## Recommended boundary

Use one explicit core grant/transfer operation, retaining the existing raw setters for classified initialization, loading, and privileged restoration. The operation should receive the target increase and an explicit donor plan; donor selection remains with each caller. Do not turn every `BaseFixedPoint` assignment into a capped player grant.

1. Compute the real sum from skill bases for both planning and final validation. Validate owner/target identity, finite fixed-point input, positive target increment, target `Up` lock and individual cap, positive valid aggregate cap, and every donor's ownership, `Down` lock, unique identity, available points, and separation from the target. Require total donor loss no greater than the target increment and final sum within cap. Rejection must change no base, donor, item budget, or reward token.
2. Calculate acceleration, individual-headroom clipping, and every donor loss before publishing any change. Reject positive grants from an already excessive real total without silently taking extra points to repair history. This preserves state pending FIX-03/FIX-04 policy; it does not normalize old saves.
3. Publish all raw bases and the accurate total before invoking existing notifications. Keep a per-owner guard throughout notifications to reject nested grants; contain and log callback failures so an already committed operation returns success and its caller consumes the reward. Recompute the cache after trusted callback writes without deleting points. A loop of individually checked public setters is not observationally atomic.
4. Consume the scroll/stone budget only after successful commit, and preserve current response-time authorization. No failure result may follow a committed base change merely because a notification threw. Test rejected nested consumption explicitly. Stored-skill removal is a separate loss/storage operation, not a positive grant.

These requirements follow `Skills.cs:556-583` (raw base setter, cache delta, then callbacks), `1453-1456` (writable cached total), `1724-1736` (invalidation/network callback), and `PlayerMobile.cs:838-867,5698-5708` (callbacks perform derived-state and young-status work). The core assembly cannot directly depend on runtime-script `PlayerMobile`; the strict transaction itself should not contain a `Player == false` bypass. Script callers must deliberately distinguish actual NPC paths from player grants.

## Trusted exceptions and audit limits

- **Serialization and construction:** preserve `Data/System/Source/Skills.cs:423-481,1621-1722` field order, versions, legacy reads and saved raw values. No serializer version or layout change is needed for an in-memory transaction guard. `System/Misc/CharacterCreation.cs:180-212,427-547` initializes a fresh character after origin setup and validates custom allocations or supplies fixed professions; do not apply ordinary reward locks to creation. These are deliberate raw initialization/load paths, not player-accessible grant exceptions.
- **NPC creation and offline clones:** `Mobiles/Base/BaseCreature.cs:9116-9142` deliberately raises NPC skill caps after assigning bases. `Custom/PvE/CloneOfflinePlayerCharacters/CharacterClone.cs:19-44` is a BaseCreature, not the source PlayerMobile. Preserve NPC setup and copy semantics. Do not infer that every `CloneThings` call is NPC-only: `Custom/NPC Control/CloneCommands.cs:597-646` also restores staff PlayerMobile state from backups.
- **Direct staff changes:** `System/Commands/Skills.cs:10-26,102-117,147-165` registers GM commands and logs concrete changes; `System/Gumps/SkillsGump.cs:64-82` rechecks GM and logs. `Custom/NPC Control/StaffCommands/GmMe.cs:10-32,54-55` is deliberately Counselor-accessible and explicitly logged. Preserve these established access levels as named privileged exceptions; do not silently elevate all of them to GM or let ordinary reward callers obtain the same bypass.
- **Clone/control/restoration:** `Custom/NPC Control/CloneCommands.cs:17-26` registers Counselor commands; clone records actor and target at 247-253. Control and backup restoration have generic command-entry evidence but no equivalent per-transfer skill snapshot. The helper itself accepts arbitrary Mobile targets (`CloneThings.cs:25-68`), so document its trusted caller set and restoration purpose instead of describing it as inherently NPC-safe. Response-time authorization hardening is separately scoped; this review does not prove every deferred staff target callback revalidates its opening-time access.
- **Concrete audit gap:** `System/Commands/ConvertPlayers.cs:15-19,47-50,57-73` is an Administrator migration that copies raw skills and then terminates/restarts. `Data/System/Source/Commands.cs:299-300` logs through EventSink only **after** the handler; `Data/System/Source/Main.cs:444-451` kills the process inside the successful handler. Therefore the normal `System/Commands/Logging.cs:157-174` command audit cannot be relied upon for successful conversion. Add a narrow explicit pre-operation migration audit or record this exception as not fully audited; do not claim all raw staff paths already satisfy the audit requirement.
- **Other loss/cap/component writes:** retain deliberate loss/reset operations and existing cap serializers. FIX-02 grant validation must use actual bases and reliable caller classification; it must not claim the wider XML identity/cache/cap-component protections scheduled for FIX-04 are complete.

## Policy choices and acceptance implications

No new human decision is required to follow the authorized lock-aware, non-destructive transaction rule. SkillStone has no source-declared lock exception (its description only says it adds to current skills); recommend Up-only and document the tightened behavior. FIX-07's request to choose/document stone lock policy is not evidence that bypass was intentional. In contrast, TestCenter is an explicit configured set mode and has a clear reason to retain its lock exception.

Use exact/reject for XML increases, preserve each existing transfer donor rule, and reject grants on already excessive totals unchanged. Changing atrophy probability, pooling scroll donors, changing stone affordability, refunding teaching overpayment, or automatically repairing historic excess would be separate consequential behavior choices; none is necessary to implement FIX-02. No broad approval pause is recommended for these excluded changes.

Meaningful controller-owned verification should cover: real sum versus falsified high/low cache; PlayerMobile with `Player=false`; target/donor locks, cap boundaries and nonpositive caps; accelerated and fractional gains; duplicate/foreign/insufficient donors; no mutation on rejected grant; callbacks observing the complete final state, throwing, reentering and making trusted raw writes; valid and rejected grants for every table row; unchanged consumables/budgets on rejection and one-time consumption on success; stale/repeated response cases; configured TestCenter behavior; trusted NPC/load/staff restoration; and unchanged save format. Preserve existing characterization evidence rather than relabeling old assertions as passing repaired behavior.

Review disposition: the proposed shared-boundary design is suitable for implementation with the above scope and audit caveat. No implementation, build, runtime script compile, actual-client, or save/load acceptance is approved by this static review.
