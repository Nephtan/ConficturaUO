**R2 — remaining stale-response coverage gap, pre-existing behavior.** `SoulStone.cs:501-504` captures only the stone, while `582-590` uses its current skill/value at response. If another authorized actor retrieves/replaces the contents after the confirmation opens, the old response can grant the replacement skill, potentially taking Down donors, despite displaying the previous skill. The removal path also opens a confirmation for current contents. `OnDoubleClick:251-255` closes only the initiating actor's gumps. This scenario does not require concurrent logins on one account: the constructable default uses `account=null` (`116-118`), and `CheckUse:184-188` restricts accounts only when Account is non-null. The changed deleted/empty/access checks do not detect a content replacement.

Minimum follow-up: pin the intended actor and displayed skill/value for the confirmation and reject changes before grant/removal; exercise a changed-content response alongside ordinary empty/deleted/repeated cases. A stable version would be stronger than value comparison if exact replacement with identical contents must also invalidate a view, but adding a serialized revision is unnecessary for the immediate mismatch. Alternatively, explicitly retain this as an unclosed FIX-07 limitation and do not claim all stale-response families passed. This review does not present R2 as a new regression in the transaction implementation.
