## Supported cap and load policy

All values below are fixed-point tenths. Baseline `System/Misc/Settings.cs:1366-1424` establishes `cap = origin + boost + Ether`:

| Component | Source-supported values |
| --- | --- |
| Origin | default 10000; savage 11000; fugitive 13000; alien 40000 |
| Configured boost | 0 through 10000 in increments of 1000, after configuration clamping |
| Ether | 0 or 5000 |

Current `TryGetSkillCap:1399-1408` validates every component before addition, so the maximum is 55000 and addition cannot overflow. It is appropriate to share this calculation across origin setup, load reconciliation, diagnostics, base-cap display and Ether completion. `SkillVerification` now uses supported components and checks fugitive profession against `SkillStart == 13000`, eliminating the false inference that a boosted default cap of 13000 is necessarily fugitive. Its preservation and bounded diagnostic path remain intact.

Origin selection deliberately resets the boost to current configuration, as baseline `SkillBegin` already did; loading retains the existing supported saved-boost floor through `max(saved,current)`. A supported lower cap alone must leave bases unchanged. The accepted core `Skills.TryGrant` independently rejects a positive grant when the real total already exceeds cap (`Data/System/Source/Skills.cs:1501-1503`); raising cap to the actual total or deleting skills would expand this repair. The explicit alien skill reset remains a separate, user-authorized origin behavior.

Legacy inference is an existing compatibility heuristic, not proof of history. The eight recognized old numeric tiers are 10000/11000/13000/40000 and their +5000 Ether variants; cap totals can otherwise overlap boosted combinations. Preserve unsupported/nonblank records rather than guessing. Calling reconciliation after the deserialize switch extends recognized all-zero-field handling to pre-version-35 saves. That is a semantic migration requiring old-save fixtures, even though the byte layout is unchanged.

The source diff preserves all reader/writer calls and the version-37 format. Current `PlayerMobile.cs:4600-4602` still reads Start, Boost, Ether in that order; `5009,5019-5021` still writes version37 and the same three ints in their original position. No type, namespace, constructor, saved field or project inclusion changes were observed. `ApproachObsidian` and `ObeliskOnCorpse` serializers are unchanged. This is source evidence, not a substitute for actual serialization/save-load checks.
